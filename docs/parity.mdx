---
title: 🧭 GUI parity
description: What pCloud's desktop client and web app can do, and which of it pcloud-cli covers, lacks, or leaves out on purpose.
---

pCloud ships two graphical clients: **pCloud Drive**, the desktop app that
mounts the virtual drive and runs sync, and the **web app**. This page lists
what they expose and, for each, where `pcloud` stands. It exists so that gaps
are chosen rather than discovered, and so that the roadmap follows from the
table instead of from whatever comes to mind next.

## Reading the table

| Status        | Meaning                                                                   |
| ------------- | ------------------------------------------------------------------------- |
| ✅ covered    | A command does it; the command is named                                   |
| 🟡 partial    | Some of it is reachable, but not the whole of what the GUI offers         |
| ❌ missing    | The GUI does it and `pcloud` does not, yet                                |
| 🚫 excluded   | Left out on purpose — the reason is given, so it is not reopened as a gap |

The **Evidence** column says how the GUI side is known, because not all of it is
known equally well:

| Evidence  | Meaning                                                                                       |
| --------- | --------------------------------------------------------------------------------------------- |
| API       | `pcloud` already calls the pCloud API method behind it, so the capability demonstrably exists |
| local db  | pCloud Drive's own database (`~/.pcloud/data.db`) holds the table or setting behind it        |
| observed  | Described from pCloud's behaviour elsewhere in these docs                                     |
| unverified | Commonly listed as a client feature, but not yet checked against pCloud's own documentation  |

An **unverified** row records a feature worth checking, not a confirmed one. It
moves to another evidence class once confirmed, or off the table if pCloud does
not offer it.

## Deliberately excluded

These are not gaps. They are recorded here so that nobody reopens them without
new evidence.

### Creating sync pairs

The daemon accepts a hand-written `syncfolder` row — and then silently never
uploads. It watches the folder and indexes new files, but never builds the
remote index a working pair carries, so files sit known and unsent while every
health check reports the pair as fine. [Local sync
inspection](/projects/pcloud-cli/docs/sync) gives the full account. `sync add`
does the unambiguous halves and leaves the pairing to the app.

### Unlocking Crypto

pCloud Crypto is zero-knowledge by design: the passphrase never leaves the
machine, and the unlocked state lives in the daemon's memory rather than on
disk. There is no row to write and no API to call. The CLI may report whether
Crypto is unlocked; it will not unlock it. Crypto key tables are never read, by
the same allowlist that keeps `sync --debug` away from credentials.

### Media playback, billing, security settings

Each has a better home than a terminal, and none blocks a workflow the CLI
exists to serve.

## The boundary that shapes the rest

Features backed by the desktop client's **local database stay read-only** unless
a write has been shown to be safe. `sync` and `settings` set that boundary, and
the sync-pair experiment above shows the cost of crossing it: a write the daemon
accepts is not the same as a write the daemon acts on.
